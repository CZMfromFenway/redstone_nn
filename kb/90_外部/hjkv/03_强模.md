# 强模（信号强度 > 15）

> 术语对照：中文 Wiki 叫**强信号模拟电路（强模）**，对照**弱信号模拟电路（弱模）**；
> 英文社区 mcdf wiki 叫 *Redstone Comparator with Invalid Signal Strength*；
> MCHPRS 官方文档叫 **High-Signal Strength (HSS)**；早期中文社区叫**超强信号**。

---

## 1. 定义

**强模 = 用比较器承载 >15 的信号强度来做模拟运算。**

「弱模」= 基于 0..15 的模拟电路；「强模」= 基于 0..2,147,483,647 的模拟电路。

**根因**：比较器的信号强度存在**方块实体的 NBT int 键 `OutputSignal`** 里（不是 4 位方块状态），
所以能超过 15，且**原版不做任何截断**。

**[Wiki]** 原文：*命令方块的 success count 在代码里可以到 32 位整数上限，
可以配合不使用红石粉的结构使用这些值。*

## 3. 三大传递性质 **[MCBBS 2014 实测 + 源码核对一致]**

| 连接方式 | 能否传强模 | 原因 |
|---|---|---|
| 红石线 | ❌ 不传 | Java 版红石线**规制**强度：>15 一律按 15，<0 直接忽略 |
| 比较器直连 | ✅ 传 | 读对方 `OutputSignal` 原值，无截断 |
| 方块充能 | ✅ 传 | 见下方 **§3.1**（原表述「取所有充能者的最大值」**不严谨，已修正**） |

**推论**：强模信号每走一步必须是 `比较器 → 方块/容器 → 比较器`，
**拐一次弯就要多一个方块 + 一个比较器**（因为比较器只能向正前方输出，不能转向）。

---

### 3.1 方块充能的真实规则：**扫描到 ≥15 就提前返回** **[hjkv 4→64 强模矩阵乘法器 全量坐实]**

> 这一条是让 MCHPRS 跑通 hjkv 作品的关键，也是我早期「取最大值」说法的**纠正**。
> 判据：schem 里烧录的 6730 个比较器 `OutputSignal`（作者自己的仿真输出，4 个通道经游戏实测）。
> 改成「取最大值」时 **1173 个不符**；改成下面的规则后 **6730 个全部吻合**。

方块充能不是简单的 `max`，而是原版 `SignalGetter#getDirectSignalTo` 的语义：

```
按 Direction.values() 顺序扫描方块的 6 个邻居 =  DOWN, UP, NORTH, SOUTH, WEST, EAST
running_max = 0
for 每个邻居:
    if 该邻居是信号源 and 它朝本方块发强充能:
        running_max = max(running_max, 它的值)
        if running_max >= 15: return running_max      # ← 提前返回，后面的不再看
return running_max
```

**后果（这是强模「门控」的物理基础）**：

| 情况 | 方块充能值 |
|---|---|
| 只被一个强模比较器（如 1779）充能 | 1779（原值穿过，不截断） |
| 同时被 **点燃的火把（15）** 和 **强模比较器（829）** 充能，且火把方向在扫描中更靠前 | **15**（15 遮蔽了 829） |

- 因为 **DOWN 排在扫描顺序的第一位**，所以**正下方的火把**总能遮蔽其它方向的更强充能源 —— hjkv 作品正是用「竖直火把塔」当门：
  每个权重桶后面隔一个方块，正下方一根火把；火把亮 → 该方块充能锁死 15 → `i < 15` 不成立 → **隔方块读容器被屏蔽**，比较器输出 15 而不是权重 W。
  这就是公式 `N = Σ (W·bit − min(0,W))` 里「15 代替 W」的物理实现（`W0 = J·K − 15·nb` 中的 `15nb` 就是这么来的）。

**配套两条（同时坐实）**：

| 规则 | 说明 |
|---|---|
| 隔方块读容器的条件 | `i < 15 && isRedstoneConductor`：**充能 ≥15（含 >15）时忽略容器**。充能 15 → 输出 15；充能 0 → 读到后面的桶值 |
| 火把的强充能方向 | **直立火把 → 只充它下方（所附）的方块**；**墙火把 → 只充它上方的方块**（不充下方）。所以「下方墙火把」能门控，而「上方墙火把」不能 |
| 实心方块作**侧**输入 | ❌ 恒为 0（`getControlInputSignal` 对普通实心方块返回 0）。侧输入只认二极管 / 红石块 / 红石粉 |

**MCHPRS 落点**：`CompileLink`/`IncomingLink` 增加 `conductor` 标记（经实心方块中继的链路），
后端 `DirectBackend::compute_inputs` 对这类链路按扫描顺序求 running max 并在 ≥15 时停止。
`BlockFace::values()` 的顺序（Bottom, Top, North, South, West, East）**恰好等于**原版 `Direction.values()` 顺序，所以链路的插入顺序就是扫描顺序，无需额外排序。

## 4. 容器信号上限：897 与 960 之谜（已解决）

**网上流传两个数字，2014 年 MCBBS 首发帖的更新给出了答案**：

> **2014/3/7 更新**
> **理论值 960，但实测结果是 897。另外如果用 NBT 方法，最大值实际上是 2147483647，orz……**

| 数字 | 含义 | 正确性 |
|---|---|---|
| **960** | `15 × 64` 的**错误推算**（误以为公式是 `15 × 满度`） | ❌ 已被作者自己纠正 |
| **897** | `1 + 14 × 64`，**实测真值** | ✅ |
| **2,147,483,647** | NBT 直写 `OutputSignal` 的 int 上界 | ✅ |

**为什么是 897 而不是 960**：公式是 `floor(1 + 满度 × 14)`，不是 `15 × 满度`。
`1 + 14×64 = 897`。

**交叉验证（我实测）**：
- mcdf wiki：64 stacks → **897**，127 stacks → **1779**（`1 + 14×127 = 1779`）✓
- 我用 1.21.1 源码语义独立枚举：木桶/箱子 27 格 → **898/898 全可达**（0..897）；
  投掷器 9 格 → 864/898，首个缺口 **804**；漏斗 5 格 → 790/898，首个缺口 **730**。
  → 与用户文档 `46_强模信号规则_待定.md` §5.2 表格 **逐格吻合** ✓

## 5. 版本矩阵（关键！）

| 版本 | 容器信号公式 | 能否 >15 |
|---|---|---|
| 1.9 – 1.12 | `f += count/min(64, itemMax)`；`min(15, ceil(f))` | ❌ 封顶 15 |
| **1.13 – 1.20.x** | `f += count/min(容器上限, 物品上限)`；`f /= 槽数`；`floor(f×14)+1` | ✅ 可到 897 |
| **1.21+** | 同上（把 `min` 挪进 `Container.getMaxStackSize(ItemStack)`） | ✅ 可到 897 |
| 1.20.5+ | NBT `Count`(byte) → `count`(int) | — |
| **26.1.2 真机实测** | 见 §6 | ⚠️ 超额堆叠仍在 NBT，但读取结果与预期不符 |

**1.20.1 源码原文**（`AbstractContainerMenu.getRedstoneSignalFromContainer`）：
```java
f += (float)itemstack.getCount() / (float)Math.min(container.getMaxStackSize(), itemstack.getMaxStackSize());
f /= (float)container.getContainerSize();
return Mth.floor(f * 14.0F) + (i > 0 ? 1 : 0);
```
**注意 1.20.1 的 `Container` 接口没有 `getMaxStackSize(ItemStack)`**，
min 是公式里手动做的 —— 所以 **1.20.1 与 1.21 的公式完全等价**。

> ⚠️ 我早期曾断言「897 是 1.21+ 才有的」，**这是错的**，1.20.1 就有。
> MCHPRS 目标版本 1.20.4 属于「可到 897」那一档。

## 6. 真机实测（MC 26.1.2，本机 `mcenv` 环境）

| 结论 | 证据 |
|---|---|
| **比较器能承载 >15** | `data merge {OutputSignal:897}` 烧录后推进 300 tick **仍保留 897** ✓ |
| **超额堆叠在 26.1.2 仍可写入** | 木桶 27 格各写 count=32/64/65 → NBT **原样保留**（count=127 被规范化成 1） |
| **subtract：side > rear → 输出 0** | 真机读到 0 ✓（与 Wiki 公式一致） |
| 容器读数与环传播仍为 0/15 | **未解决**：可能与 26.x 的容器公式变更有关，未定论 |

**未解决项的排查记录（避免重复踩）**：
1. `data merge` 不触发比较器更新 → 改用「先写 Items 再放比较器」（自检）或事后制造 NC 更新。
2. `/tick sprint` 异步 → 用 `/tick step N`。
3. `mcutil.poke` 在比较器正上方放石头会**静默失败**（比较器不是实心支撑）→ 改在侧面 poke。
4. 上述修好后，27 格 × 64 剑读到 **15**（而非 897），**1 格 × 64 剑读到 0** —— 与 1.20/1.21 源码公式对不上，
   怀疑 26.x 改了容器满度算法（可能对 count 做了 min(count, maxStack) 截断）。
   **待确认**：需要 26.x 源码或换 1.20.4/1.21 服务端实测。

## 7. mchprs 强模改造的落点

**mchprs 的容器公式本来就是对的**（`crates/blocks/src/block_entities.rs`）：
```rust
fullness_sum += count as f32 / item_type.map_or(64, Item::max_stack_size) as f32;
comparator_override: (if fullness_sum > 0.0 { 1.0 } else { 0.0 }
    + (fullness_sum / num_slots as f32) * 14.0).floor() as u8,   // ← as u8 截断！
```
→ 897.0 `as u8` 在 Rust 里是**饱和转换** → **255**。这就是 mchprs 的弱模瓶颈。

**改造必须覆盖三层**（缺一不可）：
| 层 | 文件 | 改法 |
|---|---|---|
| 方块实体 | `crates/blocks/src/block_entities.rs` | `Comparator.output_strength: u8→i32`、`Container.comparator_override: u8→i32`、`.floor() as u8→as i32`、读 `OutputSignal` 不再 `as u8` |
| 编译图 | `crates/redpiler/src/compile_graph/mod.rs` | `output_strength`、`far_input` → i32 |
| 后端 | `crates/redpiler/src/backend/direct/` | `Node.output_power` → i32；`NodeInput` 加 `max_ss`；`calculate_comparator_output` 去 15 假设 |
| 导出格式 | `crates/redpiler_graph/src/lib.rs` | `output_strength`、`comparator_far_input` → i32（**破坏性格式变更**） |

**强模下必须禁用的 pass**（依赖"只有 16 种强度"）：
- `SSSetAnalysis`：`SSSet(u16)` 位掩码；且其**终止性证明**依赖"只有有限种强度"。
- `UnreachableOutput`：依赖 SSSetAnalysis。
- `ConstantCoalesce`：假设常量只有 16 种值。
- `ClampWeights`：删 `ss >= 15` 的边（红石粉衰减上限）；强模电路无红石粉时无害，但语义要审。

**运行时输入强度的维护**（本项目踩过的坑）：
- 弱模用 `ss_counts: [u8;16]` 桶 + `last_index_positive`（把 16 字节 reinterpret 成 u128 求最大桶）。
  强模下 **>15 的值装不进桶**，且 `get_unchecked_mut` 会越界写坏内存。
- 正确做法：强模下给 `Node` 加**入边表** `incoming: Box<[IncomingLink]>`，
  运行时由 `compute_inputs(node_id)` **实时遍历入边求最大输入**（对应原版"所有充能者取 max"）。
