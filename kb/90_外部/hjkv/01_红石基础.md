## 1. 时间单位 **[TechMC]**

| 单位 | 含义 |
|---|---|
| **1 gt** (game tick) | 1/20 秒 = 0.05s |
| **1 rt** (redstone tick) | = 2 gt = 0.1s |

元件宏观延迟（gt）：**中继器 2–8**（随档位）、**比较器 2**（固定）、**侦测器 2**、红石粉 1、火把 2。

游戏主循环约 20 次/秒；mspt < 50 时 TPS = 20。

## 2. 信号强度 **[Wiki]**

- 通常是 **0..15 的整数**。红石粉每传导一格 −1，所以连续粉最多传 15 格。
- **比较器可以接受并输出 <0 或 >15 的信号**（Wiki 明写）。
  - Java 版：红石线会**规制**强度（<0 忽略，>15 变 15），所以强信号**不能上线，只能比较器链式传递**。
  - 基岩版：信号传递基于有向图，红石线只做图的边，**不规制**，>15 可上线并正确衰减，但最远仍 15 格。

## 3. 充能理论 **[TechMC]**

| 类型 | 触发者 | 效果 |
|---|---|---|
| **强充能** | 中继器、比较器、火把、侦测器**直接对着**可充能方块 | 激活周围 **6 个方向**的红石粉（不论指向） |
| **弱充能** | 可充能方块被**红石粉指向** | 只能激活输入端对着它的中继器/比较器等 |

- 「充能等级」= 用多大强度充能；与充能类型无关。
- 「可充能方块」= 大多数方块；玻璃/台阶/半砖/箱子**不可充能**（不压线）。
- 活塞/粘性活塞也定义为不可充能。
- 强充能方块表现得像红石块，但红石块**不可充能**，且能改红石粉形状与指向、可给比较器侧输入。

### 3.1 支撑规则（★ 我曾搞错，被 GPT 纠正）

**红石元件放在方块的「顶部」，所以支撑方块在正下方 `(x, y−1, z)`，不是 `(x, y, z−1)`。**

| 元件 | 需要正下方支撑？ |
|---|---|
| 红石粉 redstone_wire | **是** —— 放在 opaque 方块顶面 |
| 红石中继器 redstone_repeater | **是** |
| 比较器 comparator | **是**（且比较器非实心方块，其正上方放石头会**静默失败**） |
| 火把 / 侦测器 | 是（分别在顶面/侧面） |
| **桶 barrel** | **否** —— 完整方块，随便放 |
| **标靶 target** | **否** —— 完整方块，随便放 |
| 红石块 / 混凝土 / 玻璃 | 否（自身即完整方块） |

Wiki 原文：
> "Redstone dust can be placed on the **top** of any opaque block, or on the top of
> glowstone, an upside-down slab or upside-down stairs."
> "A redstone comparator can be placed on top of most full solid blocks..."

**推论（压缩设计的关键）**：
- 「上方支撑」与「下方支撑」是两回事，比较器**上方**可以放石头（真机上会静默失败，需在侧面 poke），
  但**下方**必须有方块否则放不上。
- 判断一个空位能否放红石元件，看的是**同 (x,z) 的 y−1 格**，不是 z−1 格。
- 完整方块类元件（桶/标靶/红石块/混凝土/玻璃）不占支撑，插进任何空位都成立。

### 3.2 ★ 「可传导」≠「可支撑」（我曾搞错）

这是两个**独立**的方块属性，混淆会得出错误结论：

| 属性 | 含义 | 玻璃 |
|---|---|---|
| **conductive（可传导）** | 能否被充能并把充能传给邻居 | **否** —— 玻璃不压线、不传递充能 |
| **sturdy / full（可支撑）** | 顶面能否承托红石元件 | **是** —— 玻璃是完整方块 |

**所以玻璃虽然不导电，但完全可以支撑红石粉/中继器/比较器。**
（Wiki 原文说红石粉放在 "the top of any opaque block"，这是简化说法；
实际判定是顶面 sturdy，玻璃满足。）

其他常见「不导电但可支撑」的：所有完整方块（玻璃、混凝土、桶、标靶、红石块、灯、告示牌…）。
「不导电且不可支撑」的：空气、火把、按钮、拉杆、红石元件本身。

**压缩设计含义**：判断某个空位能否塞一个红石元件，看的是它正下方 (x, y−1, z)
是不是一个**完整方块**，而不是「是不是可导电方块」。

### 3.3 ★ Target（标靶）的真实作用

**Wiki 原文**（Target 条目）：
> "A target is a block that produces a temporary redstone signal when hit by a **projectile**."
> "Being a **power source**, a target **redirects adjacent redstone dust** to point to itself.
> As targets are also conductive, this property can be used to compact redstone circuits."

**关键理解**：
- target 本身**不产生持续信号**（只有被箭/雪球等弹射物击中时才发 8~20gt 信号）
- target 的**设计用途是「红石粉转向器」**：它算 power source，能让相邻的粉**强制指向它**
- 因为粉连到 target 是「弱充能」，**强度不衰减**；
  而粉连到粉是「强充能但每格 −1」→ **用 target 转向可以避免衰减 1 级**
- target 自身是 **conductive**，且会**改写红石粉的连接形状**

**典型用法（模拟量通路转向）**：
```
粉(5,4,7) --[弱充能, 不衰减]--> target(6,4,7) --> 中继器(6,4,8) 读到原始强度 P --> 输出 15
```
若不用 target，粉多走一格就会从 P 变成 P−1，**模拟译码就错了**。

**实测注意（我本机验证）**：
- MC 的 target **没有方块实体**，`data get block` 会报
  "The target block is not a block entity" → **读不到它的 power NBT**
- 它的充能等级只能**通过比较器读取**来观察（比较器读 target 的充能等级）
- 红石粉的连接状态在 **BlockState** 里（不是 NBT），`data get` 同样读不到；
  要用 `execute if block <pos> minecraft:redstone_wire[east=side]` 之类逐方向判断
- 粉的连接方向 ≠ 供电方向：只有 1 个邻居时，粉会在该邻居方向和**背离方向**都显示 side
  （Wiki："If there is only one such neighbor, redstone dust forms a line pointing
  toward and away from that one neighbor"）

## 4. 三种更新 **[TechMC]**

| 类型 | 触发 | 顺序 | 响应者 |
|---|---|---|---|
| **NC 更新**（`neighborChanged`） | 方块放置/破坏、红石粉能量变化、活塞推拉… | **西东下上北南** | 绝大多数方块 `neighborUpdate` |
| **PP 更新**（`updateShape` / `getStateForNeighborUpdate`） | 除命令放置、调试棒改状态外的几乎所有变化 | **西东北南下上** | 只有**侦测器**响应 |
| **比较器更新** | 容器物品数变化、有"容量"概念的方块、物品展示框、讲台、探测铁轨矿车、雕纹书架 | — | **仅比较器** |

### 4.1 关键机制（我盲试失败的根源）**[TechMC]**

1. **比较器更新只在 `setBlockState` 里触发**：
   ```java
   if ((flags & Block.NOTIFY_NEIGHBORS) != 0) {
       this.updateNeighbors(pos, blockState.getBlock());
       if (!this.isClient && state.hasComparatorOutput()) {
           this.updateComparators(pos, block);   // ← 比较器更新
       }
   }
   ```
   → **`/data merge` 直接改 NBT 不经过 `setBlockState`，比较器永远收不到通知。**
   → 改容器内容后想触发比较器更新，必须让方块真正经历一次 `setBlockState`（如放置/破坏相邻方块产生 NC 更新）。

2. **红石元件被放置时会「自检」**（`onPlaced` → `hasPower` → 安排计划刻）。
   → **正确实验顺序：先写容器 Items，再放比较器**（放置即自检读数）。
   → 注意自检**只做一次**；之后内容变化要靠更新。

3. **方块更新不携带具体信息**，只说"这里变了"。

4. **更新核**：发 NC 更新的方块。按**西东下上北南**依次更新 6 邻居。
   - 红石粉能量变化 = **二阶毗邻**更新。
   - 带指向的红石元件（比较器/中继器/侦测器）：先单独更新**输出端指向的方块**，再以该方块为更新核发 NC 更新，**且不更新自身**。

5. **中继器/比较器的输出端**（源码 `AbstractRedstoneGateBlock.updateTarget`）：
   ```java
   Direction direction = state.get(FACING);
   BlockPos blockPos = pos.offset(direction.getOpposite());   // ← 输出端
   world.updateNeighbor(blockPos, this, pos);
   world.updateNeighborsExcept(blockPos, this, direction);
   ```
   → **输出在 `facing` 的反侧**。

6. **setBlockState 的 flag（9 位）**：`NOTIFY_NEIGHBORS=1`、`NOTIFY_LISTENERS=2`、`FORCE_STATE=16`、`SKIP_DROPS=32`、
   `MOVED=64`、`SKIP_BLOCK_ENTITY_REPLACED_CALLBACK=256`、`SKIP_BLOCK_ADDED_CALLBACK=512`（**跳过自检**）。

## 5. BUD / CUD **[TechMC]**

- **BUD**（Block Update Detector）：方块当前状态 ≠ 本应状态。
  典型：被充能但未激活的活塞（**QC 充能** = 活塞本身或正上方方块被充能）。
  BUD 响应 **NC 更新**、**不响应 PP 更新**。
- **CUD**（Comparator Update Detector）：比较器当前状态 ≠ 本应状态。
  典型：用比较器隔一个方块测堆肥桶，再把堆肥桶推走 —— 比较器仍保持输出。
  CUD 检测的是**比较器更新**。

## 6. 真机实验注意事项（本项目 `mcenv` 环境实测）

| 坑 | 正确做法 |
|---|---|
| 区块未加载 → "That position is not loaded" | 只能在已 `forceload` 的区块内操作（本环境 x∈[3,44], z∈[3,30] 区块坐标） |
| `/tick sprint N` 是**异步**的，读取会早 | **`/tick step N` 同步生效**；先 `/tick freeze` 再 `/tick step N` |
| 无玩家时红石不自动 tick | 必须手动 step/sprint |
| 改容器 NBT 后比较器不更新 | 顺序：**先写 Items，再放比较器**（自检）；或之后制造一次 NC 更新 |
| `mcutil.poke` 在比较器**正上方**放石头 | 比较器不是实心方块，石头放不下会**静默失败** → 改在比较器**侧面**（有支撑）放/删方块 |
