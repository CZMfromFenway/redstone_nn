# MLP vs D/T Duel Environment v0.3 — Training-Cost Track

## Scope
This round focuses on the user's main concern: whether D/T networks lose their theoretical advantage when network size grows because the training/search problem becomes too hard.

The comparison is still on the full 2-input state space `(x1,x2) in {0..15}^2` (256 states), binary output, using hard error count / 256 as the common ranking metric.

## 1. Search methods now separated by representation level

### Raw comparator-parameter search
Used for Sum-DDD / Sum-DDDD. A two-stage network is initialized by embedding a solved one-stage network into `2->2->1`; therefore the two-stage search begins from a functionally non-worse solution.

### Function-level Count training
For Count-DDTT / Count-DDDT, each branch is trained directly as a 16-bit unary Boolean function rather than by searching underlying comparator parameters.

To guarantee compilability:
- DDTT branch functions are constrained to <= 8 reversals (`K_full(DDTT)=8`).
- DDDT branch functions are constrained to <= 7 reversals (`K_full(DDDT)=7`).
- Each hidden `G` is selected exactly from the 739 realizable single-D analog functions.
- The final `G + threshold` is selected exactly from the 242 realizable single-D binary predicates.

Thus every function-level Count solution in this report stays inside a subset that is guaranteed to compile back into the requested D/T structure. This method may understate full DDTT/DDDT capacity because those structures also realize many functions with >K reversals.

## 2. Smooth-gradient prototypes
Two early Count relaxations were also tested:
- transition/tanh surrogate;
- straight-through / relaxed categorical prototype.

They can train some structured tasks, but currently exhibit a significant hardening/projection gap and are not competitive with function-level coordinate descent. They are retained as future scaling methods, not used for the current capacity ranking.

## 3. Sum: 3D trains more effectively than 4D after scaling to two stages
On the first four common random balanced truth tables:

| Sum architecture | one-stage mean errors | 2->2->1 mean errors | improvement |
|---|---:|---:|---:|
| DDD | 91.00 | **77.75** | **13.25** |
| DDDD | 89.25 | 84.50 | 4.75 |

Both two-stage searches used a protected embedded one-stage seed. Therefore the weaker practical gain of DDDD is an optimization/training effect rather than accidental loss of the smaller solution.

This is the first concrete evidence that deeper D chains can have more theoretical capacity while being harder to exploit after network scaling.

## 4. Count: function-level training changes the result substantially
### Structured tasks
One-stage K=8 Count recovers the certified one-stage optimum:
- `x1+x2>=16`: 40 errors
- `x1>x2`: 40 errors
- XOR: 0
- interval OR: 0

With `2->2->1`, the first two fall to 24 errors each, while XOR and interval OR remain exact.

Additional width on relational tasks:

| hidden width | sum-threshold errors | compare errors |
|---:|---:|---:|
| 2 | 24 | 24 |
| 3 | 17 | 10 |
| 4 | 13 | 12 |
| 5 | 7 | 9 |

Non-monotonic cells reflect local-search optimization noise; no topology impossibility is claimed for the remaining errors.

### Random balanced truth tables — first four common tables

| Count-DDTT width | mean errors | mean function evaluations | mean implementation wall time* |
|---:|---:|---:|---:|
| one-stage | 84.00 | 2,476 | 0.08 s |
| 2 | 69.75 | 62,874 | 1.68 s |
| 3 | 64.25 | 100,190 | 2.76 s |
| 4 | 58.50 | 143,812 | 4.17 s |
| 5 | **50.50** | 148,501 | 4.42 s |

`*` Wall time is implementation-specific Python timing and must not be treated as a hardware-independent complexity measure. Function evaluations are the more useful search-budget indicator.

The curve does not show an optimization collapse through width 5. Search cost rises sharply from one-stage to two-stage, then grows more gradually in this small experiment.

## 5. DDTT vs DDDT for Count
At hidden width 2 on the same first four random tables:
- DDTT / K=8: **69.75** mean errors
- DDDT / K=7: 72.50 mean errors

DDTT remains the primary Count candidate for the duel. DDDT remains a secondary candidate rather than being removed.

A striking preliminary pattern under these budgets is:

This does **not** establish a universal 4x width rule. It only describes this small random-truth-table pressure test.

## 7. Training-cost interpretation
The present data support three separate statements:

1. **Raw D/T parameter search scales poorly enough to hide real capacity.** DDDD's extra theoretical capacity is much harder to exploit than DDD after moving to two stages.
2. **Function-level compilation-aware training is a major improvement.** Count networks become much stronger when training operates on the already-enumerated unary function level and only later compiles back to comparator structures.
3. **The Count family should not be dropped.** It currently has the cleanest path to scalable training among the D/T candidates, although a genuinely gradient-based scalable optimizer is not solved yet.

## 8. Current duel roster after this round
- Sum route: keep DDD and DDDD; 5D remains removed.
- Count route: DDTT primary, DDDT secondary.
- Max route: retained for OR/region-like tasks but not prioritized for the random-table scaling ladder.
- MLP: tanh remains the stronger training baseline on the current random truth-table suite; ReLU remains in the official roster but is not the current crossing-point reference.

## 9. Immediate next experimental logic
The next fair scaling comparison should keep the task set fixed and extend both curves while logging training budget:
- Count-DDTT hidden width 6, 8, ... only while best error continues to improve;
- tanh MLP width 24, 28, 32 with the same restart/step budget;
- then introduce MLP-teacher and DT-teacher tasks, because purely random truth tables emphasize memorization rather than structured generalization.

Before physical-redstone conclusions, the function-level Count solutions also need a witness compiler for every learned 16-bit branch function, even though realizability is already guaranteed by the K_full constraint.
