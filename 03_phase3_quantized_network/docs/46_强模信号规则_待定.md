## 1. 一分钟速览

> **强模信号 = 比较器独占的、大于 15 的数值通道。**

**我们的电路只用到下面四个构件**（强模能用的元件当然不止这些——红石粉、中继器、活塞等同样可以用，
只是一个通用模拟器要处理它们，见 §10.2）：

| 构件              | 作用                                      | 我们是否使用 |
| --------------- | --------------------------------------- | --- |
| **比较器**         | 唯一能运算、唯一能承载 >15 的元件（compare / subtract） | ✅ 全部电路 |
| **容器**（木桶 / 漏斗） | 常数。信号强度由内容物决定，0..897                    | ✅ 只用木桶 |
| **比较器环**        | 内存。存任意大（2³¹−1）且不损耗                     | ✅ 存 K、W₀、c·2^k |
| **火把**          | 反相器 + 恒 15 的电源                          | ✅ 输入分配、塔 |
| （红石粉 / 中继器）     | 数电元件，≤15                                | ❌ 未使用 |

> 它不能像红石粉那样"拉一条线"：**信号每走一步都要经过 比较器 → 方块/容器 → 比较器**。

这条"不能拐弯"的性质是理解强模电路结构的钥匙，见 §2.2。

## 2. 信号的载体

### 2.1 只有比较器能承载 >15 ☆

强模信号指**大于 15** 的信号。比较器是方块实体，数值挂在方块实体的 `OutputSignal` 上：

**OutputSignal ∈ [0, 2³¹−1]**

**除了比较器，其他所有红石元件都无法接收或输出大于 15 的信号。**
几乎所有的红石信号元件（比较器、阳光传感器、测重压力板等少数除外）一律输出 **15**：
中继器、火把、拉杆、按钮、压力板……

★ **实测**：我们把 $K=9176$、$W_0=36224$、$36968$ 等常数直接写进比较器的 `OutputSignal`，
游戏中读出的值正确（抽查了 4 个通道，白总线沿途与头部逐级都对得上）。
层1 最大 $W_0=51168$ 未单独抽查；层2 用到 320 460，**尚未实测**，按上限规则应当没问题。

### 2.2 强模不能拐弯：中介方块是必需品 ★

这是**最容易被忽略、也最能解释强模电路长相**的一条：

**比较器只能向"正前方那一格"输出；它无法转向、无法跨格、无法与另一个比较器直接相连。**

要改变方向或跨越距离，唯一的办法是：

`比较器 → 充能一个实心方块 → 另一个比较器去读那个方块`

**推论一**：强模电路的"布线"本质是**充能方块图**，不是"线"。
每拐一次弯，就要多一个方块 + 一个比较器。

**推论二**：所谓"四个比较器首尾相连的环"，实际结构是 **4 个比较器 + 4 个中介方块**，
在平面占一个 3×3，而不是四个比较器贴在一起。§6 给出完整结构图。

> 为什么读"被充能的方块"而读数不衰减？见 §4：若方块只被比较器充能，
> 读它的比较器看到的就是**充能者的最大值**，数值原样传递。

### 2.3 各类载体能承载多大

| 东西                   |              能承载的最大值 | 能否运算                 |
| -------------------- | -------------------: | -------------------- |
| 比较器（`OutputSignal`）  |                2³¹−1 | ✅ compare / subtract |
| 容器（木桶 27 格 / 漏斗 5 格） |                  897 | ❌ 只读                 |
| 被充能的实心方块             | 取决于充能者（比较器可充到 2³¹−1） | ❌ 只被读写               |
| 火把 / 中继器 / 红石粉       |                   15 | ❌（火把恒 15，红石粉可衰减）     |

## 3. 比较器的运算 ★

**规则没有因为数值变大而改变**，只是数值大了：
```
compare:   out = rear        （当 rear ≥ side）
           out = 0           （当 rear < side）

subtract:  out = max(0, rear − side)
```

- `rear`（后方）= 比较器**面朝方向的反面**那一格，也就是它的"输入来向"。
- `side`（侧面）= 左右两侧；只有能给出数值的东西才算数（见 §4 末）。
- ★ **实测**：我们层1 的减法链（每级减去上千）、配对区的减法器，游戏里逐级数值都对得上，
  说明上式对上万量级同样成立。

## 4. 读取规则：rear 是不同东西时，比较器看到什么

这一段是全文档最需要精确的部分。按 rear（比较器**背后那一格**）分六种情形：

| rear 是什么      | 比较器看到的值                                                                   | 标记          |
| ------------- | ------------------------------------------------------------------------- | ----------- |
| **容器**（紧贴）    | 容器信号 $0..897$。**任何充能都改变不了它**，只有内容物变才变                                     | ☆⚙★         |
| **方块，且身后有容器** | 默认"穿透"读那个容器；**仅当隔着的方块被 ≥15 充能时**，才放弃容器、改输出那个更强的信号                         | ☆（⚠ 见 §4.2） |
| **方块，身后无容器**  | 看**谁充能这个方块**（有优先级时取先扫到的那个，见 §4.1）。火把/中继器充能 → **15**；红石粉充能 → 红石粉的强度（≤15）；多个比较器充能 → **不是取最大**，按扫描顺序 | ☆⚙ |
| **另一个比较器**    | 该比较器的 `OutputSignal`（这就是 §2.2 的"中介"链）                                     | ★⚙          |
| **火把**        | 15                                                                        | ★⚙          |
| **空气**        | 0 / 未就绪                                                                   | ⚙           |

### 4.1 方块被多处充能：按扫描顺序，不是取最大【修正 2026-10-31】

> **原文（错）**：能确定的只有一条——比较器的充能优先级最低；火把 / 中继器 / 红石粉之间不排序。
> 原表述的问题：① 实际并不存在一张"火把 > 中继器 > 红石粉 > 比较器"的优先级表；
> ② 比较器的优先级"并不低"；③ "取所有充能者的最大值"也是错的。

原版 `SignalGetter#getDirectSignalTo` 的语义是**按固定顺序扫描、累加到 ≥15 立即返回**：

```
running = 0
for dir in [DOWN, UP, NORTH, SOUTH, WEST, EAST]:     # 就是 Direction.values() 的顺序
    if 该方向有信号源向本方块发强充能:
        running = max(running, 它的值)
        if running >= 15:  return running            # 提前返回，后面的方向不再看
return running
```

**`DOWN` 排第一**，所以**正下方的一根火把（15）能遮蔽任何方向的更强充能**。
两个直接后果：

| 情形 | 方块充能 |
|---|---|
| 只被一个强模比较器（如 3500）充能 | 3500（原值穿过，不截断） |
| 同时被点燃的火把（15）与强模比较器（829）充能 | **15**（火把在 DOWN，先扫到就返回） |

★ 我们的位阵列正是靠这条工作的：输入块**正下方**点着火把 → 读数恒 15 → 隔方块读容器被屏蔽；
火把灭 → 穿透读到容器。

> 这条的实证：hjkv 用我们板子里 6730 个比较器的烧录值当 oracle 反推规则——
> 按"取最大"算有 **1173 个不符**，按"扫描顺序 + ≥15 提前返回"算 **6730 个全对**。
> 详见 `kb/10_游戏机制/比较器.md` §5.3、`强模.md` §3.1（C-01）。

### 4.2 穿透的 ≥15 门槛

规则是：**隔方块读容器时，只有隔着的方块被 ≥15 充能，才会打断这次"穿透"**；
若充能只有 1..14，比较器仍然读容器。

⚠ **我们目前的代码里没有这一段**，因为我们的仿真过程不涉及它：
我们板子里"隔方块读容器"的那一格只有两种状态——火把亮（15）或完全没被充能——
不存在 1..14 的中间态，所以写与不写等价。

这个机制在**另一个我们设计过、但没有做 schem、因此也没有仿真过的结构**（强模 LUT）里是要用的。
**正式代码需要按下面的顺序实现：**

```
读取 rear：
  1) 是火把        → 15
  2) 有充能 ≥ 15   → 该充能值
  3) 身后是容器    → 容器值
  4) 有充能 1..14  → 该充能值
  5) 都不是        → 未就绪（或 0）
```

### 4.3 侧位（side）的取法【修正 2026-10-31】

侧输入按比较器的**左右两个垂直方向**取，结果是 **max(left, right)，不是相加**。

**哪些东西能给侧输入**（补全）：

```
侧输入 ∈ {红石粉、红石块、中继器、其他比较器、侦测器（特定情形）}
```

**三条容易错的**：

1. **火把、按钮、拉杆不给侧输入**——它们给的是"充能"，那是另一套机制；
2. **普通实心方块作侧输入恒为 0**（源码 `getControlInputSignal` 对实心方块返回 0）；
3. `rear == side` 不算"侧输入更大"：比较模式照常输出 rear，减法模式输出 0。

> ⚠ 我们的仿真器**只承认"指向自己的比较器"当侧输入**。这是**我们的建模简化，不是游戏规则**——
> 我们所有结构的侧位都只放比较器，所以等价，但别把它写成"侧输入只能是比较器"。

## 5. 容器：怎么把内容物变成信号强度

这是我们认为对强模玩家**最实用**的一节。

### 5.1 通用公式 ★

容器有 $n$ 格。把内容物折算成"单位" $U$：

`可堆叠物品 1 个 = 1`　　`16 堆叠 1 个 = 4`　　**`不可堆叠 1 个 = 64`**

> **signal = 0**（当 U = 0）**；signal = 1 + floor(14·U / (64·n))**（当 U > 0）

- 正常装满一桶（每格 64 个可堆叠）→ U = 64n → **signal = 15**。
- **超额堆叠**：不可堆叠物品正常情况下每格只能放 1 个，但用 `/give` 或直接写 NBT 可以写出 `count:64`。
  此时每格贡献 64 × 64 = 4096 单位，即"64 格当量"：

`U = 64 × 64n`  ⟹  `signal = 1 + 14 × 64 = 897`

> **897 不是"能装 1728 个物品"，而是"27 格各塞 64 个叠 1 物品"。**

### 5.2 三种容器的可达性 ★

$n$ 不同，可达信号不同：

| 容器 | $n$ | 可达信号 | 缺口起点 |
|---|---:|---|---:|
| **木桶 barrel** | 27 | **898/898（100%）** | 无 |
| 投掷器 dropper | 9 | 864/898（96.2%） | 804 |
| 漏斗 hopper | 5 | 790/898（88.0%） | **730** |

**漏斗在 730（≈ 0.814 × 897）以上有一段无解；木桶全可达。**

**所以做常数优先用木桶**：同样的值，桶只需要更少的格数，且没有无解区间。
（投掷器需要活塞/随机器，一般不用来存常数。）

### 5.3 反解器：给定信号，求内容物

这是我们为了生成上万组容器而写的求解器核心（`src/barrel_palette.py`）。
它做的是**反解**：给定想要的信号 $S$，找出物品组合。**这段代码就是 §5.1 公式的可执行版**。

```python
SLOTS = 27
DENOM = 64 * 27          # 1728

def sig_of(fill_num):
    """正向：填充单位 → 信号强度"""
    return 0 if fill_num == 0 else 1 + (14 * fill_num) // DENOM

def build(s, prefer_min_items=True):
    """反解：信号 s → Items 列表。返回 (items_str, fill_num) 或 None（无解）。
       fill_num = 64*A + R，A = 木斧数，R = 红石数；A 每 64 个占一格，R>0 各占一格。"""
    if s == 0:
        return "Items:[]", 0
    lo = max(1, math.ceil((s - 1) * DENOM / 14))
    hi = math.ceil(s * DENOM / 14) - 1
    cands = []
    for fill in range(lo, hi + 1):          # 该信号对应的 fill 区间
        A, R = divmod(fill, 64)
        if A == 0 and R < 1:
            continue                        # 坑①：fill 必须 ≥1，否则生成空桶、回算成 0
        slots = math.ceil(A / 64) + (1 if R > 0 else 0)
        if slots <= SLOTS:                  # 坑②：余数会多占一格，必须在这里卡住
            cands.append((fill, A, R, slots))
    if not cands:
        return None
    fill, A, R, slots = (min(cands, key=lambda t: t[0]) if prefer_min_items
                         else max(cands, key=lambda t: t[0]))
    parts, slot, left = [], 0, A
    while left > 0:                         # 木斧每格最多 64 个
        c = min(64, left)
        parts.append(f'{{Slot:{slot}b,count:{c}b,id:"minecraft:wooden_axe"}}')
        left -= c; slot += 1
    if R > 0:
        parts.append(f'{{Slot:{slot}b,count:{R}b,id:"minecraft:redstone"}}')
    return "Items:[" + ",".join(parts) + "]", fill
```

**两个必须知道的坑**（我们各踩过一次）：

1. `S=1` 时若取 `fill=0`，会生成空桶，读回来是 0 而不是 1。所以下界要取 `max(1, ·)`。
2. **865..896 这一段**：若固定取"最小可行 fill"，余数 $R>0$ 会多占一格，
   于是需要 28 格、超过桶的 27 格。正确做法是在可行区间里搜一个 $(A,R)$，
   使 `ceil(A/64) + [R>0] ≤ 27`。

验证：把生成的 898 个容器逐个与一期数据包里已有的 512 个容器文件比对，**0 个不符**。

## 6. 环：存 897 以上的值

容器封顶 897（§5），命令方块虽然能更大但工程上通常禁用。所以：

> **大于 897 的常规存法就是比较器环。**

### 6.1 结构：4 个比较器 + 4 个中介方块

由 §2.2，比较器之间不能直接相连，所以最小环是 **3×3 里的 4 个比较器 + 4 个角块**：

```
            cL        cM        cR
          （左列）  （中列）  （右列）
        ┌─────────┬─────────┬─────────┐
  r0    │  角块 V │ ⬅ 比较器 │  角块 V │   中列比较器：读右角块 → 写左角块
        ├─────────┼─────────┼─────────┤
  r0+1  │ ↓比较器 │         │ ↑比较器 │   左/右比较器：读上方角块 → 写下方角块
        ├─────────┼─────────┼─────────┤
  r0+2  │  角块 V │ ➡ 比较器 │  角块 V │   中列比较器：读左角块 → 写右角块
        └─────────┴─────────┴─────────┘

  箭头 = 该比较器把值写向哪一格（它的 facing 指向反方向）
```

四个比较器依次读**下一个角块**、写**再下一个角块**，四步闭合。
精确的朝向（`facing` = 输入来向 = 它读的那一侧）：

| 比较器位置 | 模式 | `facing` | rear（读） | 输出（充能） |
|---|---|---|---|---|
| 中列·上行 (cM, r0) | `compare` | `east` | 右上角块 (cR, r0) | 左上角块 (cL, r0) |
| 左列·中行 (cL, r0+1) | `compare` | `north` | 左上角块 (cL, r0) | 左下角块 (cL, r0+2) |
| 中列·下行 (cM, r0+2) | `compare` | `west` | 左下角块 (cL, r0+2) | 右下角块 (cR, r0+2) |
| 右列·中行 (cR, r0+1) | `compare` | `south` | 右下角块 (cR, r0+2) | 右上角块 (cR, r0) |

`环路：(cR, r0) → (cL, r0) → (cL, r0+2) → (cR, r0+2) → (cR, r0)`

每个比较器的侧位都是空的（`side = 0`），所以 `compare` 就是"原样复制"，
四个角块恒等于同一个值 $V$ —— **写进去多少，就是多少，不会衰减**。

★ 我们的层1 用这种环存了 K = Σ S（灰环）与 W₀ = J·K − 15nb（白环），
例如通道 0：四个角块都等于 $K=9176$、都等于 $W_0=36224$，游戏里读数一致，实测通过。

> **值不变的前提：不去动这四个比较器本身，也不去动它们充能的角块。**

### 6.2 写 `.schem` 时最致命的一个坑 ★

> **比较器的方块状态 `powered` 必须与方块实体里的 `OutputSignal` 一致。**

`OutputSignal` 在方块实体里，`powered` 在方块状态里，两者一致环才成立。
**如果全写 `powered=false`，环会失效（读数被清零）**——我们踩过。

## 7. 火把：反相器与电源

§4.1 已给出核心：**亮火把给"正上方"那格方块充能，使其读数恒为 15**。
先把一条容易搞反的前提说清，再列两条做电路必用的性质：

> **火把永远不充能自己附着的那一格方块。** 所谓"从下方充能"指的是：火把在下面，
> 它给**上方那一格**方块充能（充电面是那格的底面）——墙火把、直立火把都一样。
>
> 这条直接决定了我们塔底反相级怎么搭：把直立火把放在 A(0) 的**正下方**，
> 它才会去充 A(0)；放在旁边贴着 A(0) 是不充的。

| # | 性质 | 用途 |
|---|---|---|
| 1 | 亮火把给**正上方**的方块充能（15） | 给"输入块"点 15 |
| 2 | 火把在其**支撑块被充能时熄灭** | 反相器 |
| 3 | 墙上的火把，`facing` 指向**离开支撑块**的方向（支撑在反方向） | 决定火把搭在哪 |

> **注意：比较器的 `facing` 是"输入来向"，火把的 `facing` 是"离开支撑块的方向"。**

**这两个约定相反。混用会让整片电路接反**——这是我们踩过的最贵的坑之一。
（比较器/中继器的 `facing` 是"输入来向"，是因为原版放置时 `facing` 取的是玩家朝向的反面。）

## 8. `.schem` 里的数据格式示例

以下都是我们实际生成、并在 Minecraft 1.21 里成功加载的文件格式
（Sponge Schematic v3，`DataVersion = 3953`）。

### 8.1 比较器

方块状态（`facing` = 输入来向，`mode` = `compare` / `subtract`，`powered` 必须与 `OutputSignal` 一致）：

```
minecraft:comparator[facing=north,mode=subtract,powered=true]
```

方块实体（数值在这里）：

```nbt
{
  Id: "minecraft:comparator",
  Pos: [x, y, z],
  Data: {
    id: "minecraft:comparator",
    OutputSignal: 6685          // int，0 .. 2^31-1
  }
}
```

### 8.2 木桶（容器）

方块状态：

```
minecraft:barrel[facing=up,open=false]
```

方块实体。`Items` 里每个元素是 `{count, Slot, id}`；**超额堆叠就是把 `count` 写成 64**
（该物品本身上限是 1）：

```nbt
{
  Id: "minecraft:barrel",
  Pos: [x, y, z],
  Data: {
    id: "minecraft:barrel",
    Items: [
      { count: 64, Slot: 0,  id: "minecraft:wooden_axe" },
      { count: 64, Slot: 1,  id: "minecraft:wooden_axe" },
      /* … 共 27 格，每格 64 个木斧 … */
    ],
    CustomName: '"signal: 897, item: 1728x64"'   // 只是注释用，游戏不解析
  }
}
```

`27 格 × 64 个叠 1 物品  ⟹  U = 64 × 64 × 27  ⟹  signal = 897`

> 早期版本（1.20.5 之前）物品计数键叫 `Count`（byte），之后改成 `count`（int）。本文按 1.21 的写法。

### 8.3 其他必须遵守的格式细节

| 项 | 要求 | 否则 |
|---|---|---|
| 文件名 | **全 ASCII** | 加载器失败 |
| 结构根层 | 必须有 `Schematic` 这一层（`(根,空名) → Schematic → Blocks`） | WorldEdit 报 unknown error |
| `Data` 长度 | 必须等于 `W × H × L` | 加载错位 |
| 容器信号 | **≤897**（木桶） | 超出即不可达，只能靠环 |
| `powered` | 与 `OutputSignal` 一致 | 环失效（§6.2） |

写给要自己写解析器的人：**TAG_Long_Array 读完必须把游标前进 `8×n`**，
否则解析立刻失步，会误判"文件格式错误"，而其实文件是对的。

## 9. 求值算法：没有游戏时怎么验证电路

强模电路里有**闭环**（环），所以"反复迭代直到稳定"**不工作**：会震荡，也会"早锁"
（rear 一就绪就定值，可侧输入还没算出来，于是整条链错）。

我们用的算法：

```
① 锁源：所有环的比较器按烧录值直接锁定，并把它们的输出登记为"已充能"。
② 拓扑推进：反复扫描未锁定的比较器；
   若 (a) rear 已可解析，且 (b) 所有"指向自己的侧位比较器"都已锁定
   → 按 §3 算出值、锁定，并把它充能的方块登记。
③ 直到没有新的可锁定。
```

四条经验（都来自实际踩坑）：

1. **只有环是"源"**。建板时给的 `init` 只是种子值，不是源。
2. **rear 可解析 ≠ 可以定值**：必须等侧位全部锁定，否则会提前定值。
3. **"充能"是异步写事件**：读一个方块前，要确认**它的所有充能者都已锁定**。
4. **朴素迭代的失败是静默的**：我们曾迭代 400 轮，链还停在 `1542 / 0 / 0 / 0`（只有首格对），
   表面上看不出错。

## 10. 这些规则从哪来、边界在哪

### 10.1 工程背景

我们要编译的是一个 4 → 64 → 32 的量化 MLP：

- **矩阵乘法**：每个权重拆成 8 个位权重，每格一个容器存 $15+|W|$；最高位（可达 1764）超过容器上限
  897，于是用环存；四条减法链 + 白环把总和算成"头部输出"。
- **输入分配**：n × b 根竖直"火把塔"，一根塔管一个 (输入, 位) 在全部通道上的火把。
- **输出级（除法）**：8 位 restoring division；每一位用环存 c·2^k，用"比较器 + 减法器"做条件减法。

三样东西全部由本文 §3–§7 的规则推出，反过来也说明这些规则够用。

### 10.2 现有脚本实现了什么、没实现什么

我们的脚本是为了**把上述网络编译成 `.schem` 并验证正确性**而写的，所以只实现了
"当前结构用得到的最小规则集"：

| 已实现 ⚙ | 未实现 ⚠ |
|---|---|
| 比较器 compare / subtract | 中继器 |
| 火把（恒 15 + 反相 + `facing`） | 红石粉（含衰减、方向、爬坡） |
| 容器（木桶；信号公式 + 反解） | 漏斗/投掷器的传输行为 |
| 实心方块充能（多个取 max） | 活塞、投掷器随机化 |
| 环（方块中介版） | 穿透的 ≥15 门槛（见 §4.2） |
| 直读容器、隔方块读容器 | 命令方块 |
| 侧输入只认比较器（建模简化） | 侧输入来自红石粉/中继器（见 §4.3） |

**这些"未实现"不是否定规则，而是当前结构用不到。** 但若照着做别的电路，需要自己补。

### 10.2b 想做通用模拟器，必须再加什么

如果有人要写一个**既能量强模、又能量数电**的模拟器（hjkv 想做的应该就是这个），
下面这些不能省——它们是数电那一半的全部内容：

| 元件 | 必须建模的性质 |
|---|---|
| **红石粉** | 信号 $0..15$ **逐格衰减** 1；连接方向（点状 / 线状 / 十字）；指向元件的规则；向上爬 / 向下传；被强充能时表现为 15 |
| **中继器** | 输入 ≥1 就输出 **15**；**有延迟**（1..4 tick）；**单向**；被侧面锁存（locking） |
| **火把** | 恒 15、反相、`facing`（§7）；**点燃 / 熄灭有 2 tick 延迟**，会形成时钟 |
| **比较器** | 本文 §3–§4；另有 **2 游戏刻（1 红石刻）** 延迟【修正 2026-10-31：原写 1 tick】 |
| **活塞 / 粘性活塞** | 推动、阻挡、改变充能关系（会破坏"方块是静态的"这个假设） |
| **投掷器 / 漏斗** | 物品移动 → 容器内容物会变（我们只当容器是常量） |

> **只模拟强模，可以跳过红石粉和中继器；但要模拟数电，这两样是必需的。**

我们的做法是**放弃数电那半**：整个网络里没有任何红石粉、中继器、活塞，
所以用一个"只有比较器 + 火把 + 容器 + 实心方块"的极简模型就够了。这也是我们能把
求值算法做得这么简单（§9）的前提。

## 13. 附：czm 原始口述（汇总版）

以下是 2026-10-25 的原始口述，**基本保留原话**，只做了断句与编号。
本文其余章节是对它的展开、核对与补充；每条的 §x 指展开它的位置。

**① 信号定义**
强模信号在 Minecraft Java 版中指一种只能通过比较器传输的**大于 15** 的信号。
比较器是方块实体，信号标签是 `OutputSignal`，这个键的值可以是 0 到 2³¹−1。　→ §2.1

**② 谁能承载**
除了比较器，其他所有红石元件无法接收或输出大于 15 的信号。几乎所有的能输出红石信号的元件
（除了比较器、阳光传感器、测重压力板等）都会直接输出强度为 15 的红石信号，
代表案例是中继器、火把、拉杆。　→ §2.1

**③ 运算不变**
比较器传输强模信号时，比较模式和减法模式的规则照旧，只是信号大了而已，规则不变。　→ §3

**④ 读被充能的方块**
如果比较器的信号来源是被充能的方块（且方块背后没有容器可以检测），那么这个比较器输出的信号
得看**是谁充能这个方块**。若充能这个方块的是另一些比较器，那么输出的信号是充能者中信号更大的那个；
如果这个方块被中继器、火把或者红石粉充能，哪怕这个方块同时被比较器充能，比较器对该方块的充能
都会被忽略，输出比较器必然输出 0~15 的信号。对于中继器充能和火把充能，就会输出 15；
对于红石粉充能，就会输出红石粉的信号值（红石粉的最大信号也是 15）。　→ §4、§4.1

**⑤ 直读容器**
如果比较器不隔方块直接检测容器，那么任何充能和其他影响都无法改变这个比较器检测到的容器值，
除非容器内容物本身改变。　→ §4

**⑥ 隔方块读容器**
比较器可以隔着方块检测身后的容器。只有当间隔方块受到信号强度**大于等于 15** 的充能时，
比较器才会放弃检测那个容器，转而输出这个更强的信号。这个信号可以来自火把强充能、中继器强充能、
红石粉（强度 15）充能或信号强度大于等于 15 的比较器的充能。　→ §4.2

**⑦ 容器的信号与可达性**
关于容器。在纯粹数模意义下（无活塞无投掷器），只有漏斗和木桶是有意义的容器。
通过过量堆叠不可堆叠物品，可以让容器输出大于 15 的信号，这个上限是 **897**。
对于木桶，0~897 的信号强度都有解（解指的是实现这个信号强度需要的容器物品组合）；
对于漏斗，靠近 897 的一些信号是无解的，到大约 **0.8 × 897** 左右以下的信号对漏斗都可解。　→ §5

**⑧ 环**
命令方块，作为可以被比较器检测的东西，可以输出超过 897 直到强模上限的强度的信号。
但是红石作品一般要求不出现它。所以通常存储超强模（大于 897 信号）的方法是比较器环。
最简形式是四个比较器首尾相连，其中存储的信号将不生不灭
（除非外部干预比较器和这四个比较器充能的方块）。　→ §6

> **对第 ⑧ 条的一处补充**：所谓"四个比较器首尾相连"**必须有中介方块**——
> 强模信号在没有方块中介时甚至不能拐弯。所以实际最小结构是 **4 个比较器 + 4 个角块**（3×3），
> 见 §2.2 与 §6.1。这句补充是我们后来确认的，不在原始口述里。
