# 强模：大于 15 的模拟信号

状态: 待验
可信度: 源码 + 实测（hjkv 2026-10-31 提供）+ 我们自己的枚举核对
最后核实: 2026-10-31
适用: Java 版 1.13 及以上（1.13 起容器可读出 >15）；基岩版部分性质不同，见 §5

---

## 引言

“强模”不是某种新元件，而是一个**用法**：把比较器的 `OutputSignal` 当成数值通道，用大于 15 的值来做模拟运算。

$$\text{弱模}=\{0,\dots,15\}\qquad\text{强模}=[0,\ 2^{31}-1]$$

为什么能这样？因为比较器的强度**不在 4 位的方块状态里**，而在**方块实体的 NBT int 键 `OutputSignal`** 里。
原版对它**不做任何截断**，所以它可以一直涨到 int 上限。

代价是：一旦离开比较器，这个数就活不下来（见 §3）。整座强模电路，都是围着这条限制设计的。

## 符号

| 符号 | 含义 |
|---|---|
| `OutputSignal` | 比较器方块实体里的 int，比较器的强度就存在这儿 |
| $s$ | 某一点的信号强度，强模下可 >15 |
| $i$ | 方块充能等级 |
| DOWN…EAST | `Direction.values()` 的扫描顺序 |

## 二、它从哪来：三条能拿到 >15 的路

| 路径 | 怎么拿到 | 上限 |
|---|---|---|
| 容器超叠 | 一格里塞 64 个不可堆叠物品 | 897（单容器） |
| 比较器环 | 4 比较器 + 4 中介方块首尾相接，把值存住、逐级加减 | $2^{31}-1$ |
| 命令方块 | 比较器读命令方块的 `success count` | $2^{31}-1$ |

第三条最省事，也解释了 Wiki 那句“命令方块的 success count 可以到 32 位整数上限”的实际意义：
**不写 NBT 也能拿到强模，只要让命令方块成功执行足够多次。**

## 三、三条传递性质

| 连接方式 | 能否传强模 | 原因 |
|---|---|---|
| **红石线** | ❌ 不传 | Java 版红石线会**规制**强度：>15 一律按 15，<0 直接忽略 |
| **比较器直连** | ✅ 传 | 直接读对方的 `OutputSignal`，原值、不衰减 |
| **方块充能** | ✅ 传 | 但要看 §3.1 的扫描顺序 |

**推论（整座强模电路的长相由此决定）**：

$$\text{每一步都必须是：比较器}\ \to\ \text{方块/容器}\ \to\ \text{比较器}$$

比较器只能向正前方输出，不能转向；所以**每拐一次弯就要多一个方块 + 一个比较器**。
强模电路看起来像“一堆方块和比较器”，不像“线”，根子就在这里。

> 基岩版不同：它的信号传递是**有向图**，红石线只做图的边、**不规制**强度，>15 可以上线并正确衰减，
> 但最远仍然只有 15 格。

### 3.1 方块充能：扫描顺序，不是取最大值

一个方块被多处充能时，读它的比较器看到的值**不是最大的那个**，而是：

```
running = 0
for dir in [DOWN, UP, NORTH, SOUTH, WEST, EAST]:
    if 该方向有信号源向本方块发强充能:
        running = max(running, 它的值)
        if running >= 15:  return running      # 提前返回
return running
```

**`DOWN` 排第一**，所以正下方的一根火把（15）能遮蔽任何方向的更强充能。
这条既解释了“火把塔为什么能当门”（见 `比较器.md §5.3`），也修正了流传很广的“取最大值”。

## 四、容器信号上限：897，以及“960”是怎么来的

| 数字 | 含义 | 正确性 |
|---|---|---|
| **960** | 早年按 $15\times64$ 推的，误以为公式是“15 × 满度” | ❌ 已被提出者本人纠正 |
| **897** | $1+14\times64$，实测真值 | ✅ |
| $2^{31}-1$ | 直写 NBT `OutputSignal` 的上界 | ✅ |

公式是 $\lfloor1+\text{满度}\times14\rfloor$，不是 $15\times\text{满度}$：
满度 64 时 $1+14\times64=897$。

**交叉验证**：按源码语义独立枚举三种容器，木桶 898/898 全可达、投掷器 864/898（首缺口 804）、
漏斗 790/898（首缺口 730）——与 `容器信号.md` 的表逐格一致。
另外 127 格当量（`1+14×127`）给出 **1779**，是 mcdf wiki 记录过的另一个可用常数。

## 五、版本矩阵（用别人的资料前先对版本）

| 版本 | 容器信号公式 | 能否 >15 |
|---|---|---|
| 1.9 – 1.12 | `f += count/min(64, 上限)`；再 `min(15, ceil(f))` | ❌ 封顶 15 |
| **1.13 – 1.20.x** | `f += count/min(容器上限, 物品上限)`；`/n`；`floor(f×14)+1` | ✅ 可到 897 |
| **1.21+** | 同上（把 `min` 挪进 `getMaxStackSize`） | ✅ 可到 897 |
| 1.20.5+ | 物品 NBT 从 `Count`(byte) 改成 `count`(int) | — |

1.20.1 的源码（`getRedstoneSignalFromContainer`）：

```java
f += (float)itemstack.getCount() / (float)Math.min(container.getMaxStackSize(), itemstack.getMaxStackSize());
f /= (float)container.getContainerSize();
return Mth.floor(f * 14.0F) + (i > 0 ? 1 : 0);
```

**1.20.1 与 1.21 完全等价**——差别只是 `getMaxStackSize(ItemStack)` 这个重载后来被挪进了接口。
所以“897 是 1.21 才有的”这个说法是错的，1.13 就有。

> 版本还影响 `OutputSignal` 的类型宽度。MCHPRS 原本把容器读数 `as u8` 存，
> 897 饱和成 255——这是它跑不了强模的直接原因，改造要覆盖方块实体、编译图、后端、导出格式四层。

## 判据与反例

1. **强模不能走红石粉。** 一走就被规制回 15，且每格还 −1。想在粉上“看到”强模是看不到的。
2. **别用“取最大值”算方块充能。** 是扫描顺序 + 累加到 ≥15 立即返回；DOWN 最先。
3. **别把 897 当“容器容量”。** 它是“每格超叠到 64”的产物；正常堆叠的容器上限是 15。
4. **别跨版本引数。** 1.12 及以前读不出 897；1.20.5 之前物品 NBT 是 `Count`(byte)。
5. **别把强模当“更快的弱模”。** 它每走一步都要经方块或容器，延迟和体积都比弱模贵，只在“必须大于 15”时才用。
