## 一、修的是什么

`41` §三 记的缺陷：配对区**情形Ⅱ**（一路 |W| > 882、另一路 ≤ 882）没有独立结构，
和情形Ⅰ 走了同一条路 —— 一律建 Δ 桶（= |S_big − S_small|）+ 减法器。

而情形Ⅱ 的 Δ 可以到 1749，远超单容器上限 897，于是 Δ 桶在游戏里装不下。

按 `40` §5.3 的分情形表，本来就是：

| 情形 | 条件 | 大值列 | 小值列 |
|---|---|---|---|
| Ⅲ | 两路都 ≤ 882 | 直通桶 | 直通桶 |
| **Ⅱ** | 一路 > 882 | **环** | **直通桶**（本文件修的） |
| Ⅰ | 两路都 > 882 | 环 | 减法器输出 |

**文档一直是对的，错的是代码。**

## 二、先说尺子：为什么以前测不出来

仿真器里容器**可以存任意数**（`barrel.val` 直接用），而游戏里不行：

```
容器 signal = 1 + floor(14·fill/27)，木桶 27 格、每格 ≤64
⇒ fill ≤ 27×64 = 1728 ⇒ signal ≤ 1 + 14×1728/27 = 897
```

`compiler.py` 的 `LIMIT=882`、`40` §8.3 的 897 都指向这条硬约束。但
`sweep_options.js` 只看"头部输出 N 对不对"，**不检查任何格子能不能建造**，
所以它对情形Ⅱ 是瞎的：

> 改动前的实测：`1536 / 1536` 全过，而同时有 47 个 Δ 桶装不下。
> 更关键的是 —— sweep 抽样的通道 20 / 31 / 63 **本身就是受影响的通道**，
> 它照样全绿。**不是抽样不够，是尺子没有这一维。**

### 新尺子

`viewer/plane_sim.html` 里新增 `legalCheck(B)`，判三条：

| 判据 | 含义 |
|---|---|
| `barrel.val ∈ [0, 897]` | 容器放得下（897 是 27 格全塞 64 个叠 1 物品） |
| `cmp.state ∈ [0, 2^31−1]` | 比较器 `OutputSignal` 上限 |
| `cmp.state !== undefined` | 拓扑必须全部解开（`40` §11.7） |

`sweep_options.js` 与 `dump_planes64.js` 都接上了它。**导出前必须先过合法性**，
`dump_planes64.js` 不通过直接 `exit 1`，不许写 `planes64.json`。

### 红灯证据（改情形Ⅱ 之前）

```
1536 / 1536                        ← 老指标：全绿
物理合法性: 768 / 1536
  ✗ 违规格 768 个
    i0b0: 192/192   i0b1: 192/192   i1b0: 192/192   i1b1: 192/192
```

768 = 3 个受影响通道 × 4 个 b × 32 选项 × 2 输入，每组合恰 1 个坏格 —— 与
"47 个坏 Δ 桶分布在若干通道"完全自洽。

## 三、改法（`viewer/plane_sim.html` 配对区）

大值列在 Ⅰ、Ⅱ 里完全一样，**只有小值列分家**：

```
Ⅰ、Ⅱ 共用（大值列 bigCol 走环）
    (bigCol,Z6) 从环角块取电           ← 比较器
    (bigCol,Z5) 导线
    (bigCol,Z4) 读导线                 ← 比较器
    (bigCol,Z3) 充能 MSB 块(Z2)        ← 比较器
    环：3 列 × 3 行，Z = Z7..Z9（四个 src 角块 + 两个中列比较器）

情形Ⅰ（两路都 >882）
    (xa+1,Z3) Δ 桶 = smax − smin       ← Δ < 882，一定放得下
    (xa+1,Z4) 读 Δ 桶（只作侧输入）
    (xa+1,Z5) 减法器                   ← side = Δ，rear = 大值列 Z5 导线
    (smlCol,Z5) 减法结果导线
    (smlCol,Z4) 读导线 → (smlCol,Z3) 充能 MSB 块

情形Ⅱ（一路 ≤882）—— 本文件新增
    (smlCol,Z4) 直通桶 = S_small        ← S_small ≤ 897，恒可达
    (smlCol,Z3) 直接读桶并充能 MSB 块
    不建：Δ 桶、减法器、Δ 读入比较器、小值列 Z5 导线
```

修好后 ch2（情形Ⅱ，Δ=1546，改前**装不下**）的配对区：

```
Z=9 | rx1:导线  rx2:环*1779  rx3:导线
Z=8 | rx1:环*1779              rx3:环*1779
Z=7 | rx1:导线  rx2:环*1779  rx3:导线
Z=6 | rx1:取电 1779                       ← 大值列从环上取电
Z=5 | rx1:导线
Z=4 | rx1:大值 1779            rx3:直通桶 233   ← 小值列再不经减法
Z=3 | rx1:1779                 rx3:233          ← 直接读桶，充能 MSB 块
```

## 五、现在这份 `layer1_stack64.schem` 是什么

```
results/schem/layer1_stack64.schem   58.0 KB
  14 × 128 × 31        通道 ch 在 y = 2ch+1（小通道在下），支撑方块在 y = 2ch
  比较器 6730   容器 1948   支撑方块 6730（白色混凝土）   BlockEntities 8678
  火把 0 个 ← 输入被钉死成 X=(0,0,0,0)；火把塔未做
```

> **支撑方块用 `white_concrete`**（2026-10-25 由 `smooth_stone` 改）。注意白色混凝土同时也是
> 白环/白总线的材质，所以**任何"按材质计数"的统计都会混**——`schem_stack64.py` 的支撑块计数已改成
> 按 `y % 2 == 0` 数，`schem_verify_stack.py` 的检查本来就是按位置（比较器正下方）判的，不受影响。
>
> **环内导线用 `pink_concrete`**（2026-10-25 由 `magenta_concrete` 改）：位 7 的输入块本身就是品红混凝土，
> 与导线撞色，读图时分不开。改导线不动位色，调色板 20 → 21 个。

回读对账（`schem_verify_stack.py`）逐项：

| 项 | 结果 |
|---|---|
| NBT 完整性 | 1544671 / 1544671 字节，Data 55552 = 14×128×31 ✓ |
| 逐格对账 | 12864 cell（比较器 6730 / 容器 1948 / 其它 4186），**0 处不一致** |
| 容器可达性 | 最大 897，**不可达 0 个** ✓ |
| `powered` 一致性 | true 6725 = `OutputSignal>0` 6725，false 5 ✓ |
| 容器信号反解 | 由 `Items` 的 `fill` 用 `1+floor(14·fill/27)` 重算，与仿真一致 ✓ |

> 那 5 个 `powered=false` 是**合法**的：它们在 `(x=11, Z=−18)` 即头部减法器上，
> 对应 5 个"没有负权重"的通道 —— X=0 时 N=0。不是缺陷。
